# 云同步 / 版本历史 计划

> 状态:待实施(已决策要做;后端方案待定)
> 依赖:roadmap.md §6.1

## 1. 目标

文档云端备份 + 版本快照 + 恢复。这是唯一超出本地 Tauri 能力的 P5 项,需要一个后端。

## 2. 已决策(2026-08-14)

| 决策 | 结论 |
| --- | --- |
| 同步粒度 | **文件级快照**:保存时上传整个 .docx,不做实时协作 |
| 版本粒度 | **每次保存快照**:Ctrl+S / 自动保存都存一个版本 |
| 后端选择 | **待定**:需盘点现有后端/基础设施 |

## 3. 后端方案(待定,第一步先盘点)

候选(需用户盘点后定):

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 自建服务(REST + 存储) | 完全可控、可做版本元数据/搜索 | 需维护后端 |
| 对象存储(S3/OSS/COS) | 免服务、直传、成本低 | 版本元数据需客户端或额外索引 |
| 第三方文档云(语雀/飞书/坚果云) | 零后端 | 受制于第三方 API/限流 |

**盘点项**(确定后端前需澄清):

1. 是否已有可用的后端/云账号/对象存储?
2. 用户规模(单人/团队)、文档量级、存储预算。
3. 是否需要多设备同步,还是仅备份+历史。

## 4. 客户端架构草图

```
保存(Ctrl+S / 自动保存)
  → docx buffer(现有 save 流程)
  → 计算内容哈希(去重,内容未变则不存新版本)
  → 上传快照:完整 .docx + 元数据(path/时间/哈希/大小/设备)
  → 版本列表 UI:时间线(文件名/时间/大小),可下载/恢复
  → 恢复:下载版本 → 覆盖当前 buffer → 编辑器 reload
```

**Tauri 命令**(Rust 侧,与 officecli_exec 同层):

| 命令 | 作用 |
| --- | --- |
| `cloud_upload(buffer, meta)` | 上传一个快照 |
| `cloud_list_versions(doc_id)` | 列某文档的版本时间线 |
| `cloud_download(version_id)` | 下载某版本 → reload 编辑器 |
| `cloud_restore(version_id)` | 恢复:下载 + 覆盖当前 + reload |

**版本模型**(文件级快照 + 每次保存):

- 每个快照 = 完整 .docx 文件(而非 diff);内容哈希去重,相同内容不重复存。
- 元数据:`{ doc_id, version_id, timestamp, size, sha256, device, path }`。
- 版本列表按时间倒序,支持"恢复为历史版本"。

**冲突处理**(文件级快照,简化):

- 单设备:无冲突。
- 多设备:最后写入胜(覆盖),恢复历史版本时提示会覆盖当前(二次确认)。
- 不做实时合并(已决策文件级快照,天然规避 CRDT 复杂度)。

## 5. 认证与安全

- 复用现有 Keychain + API key 凭据体系(`saveApiConfig` → `sync_credentials_to_pi`)。
- 上传走 HTTPS;凭据存 Keychain(不落盘明文)。
- 快照端到端加密可选(待后端方案定,若对象存储可考虑客户端加密)。

## 6. 里程碑

1. **M1 后端盘点**(§3):确认方案 → 更新本文档。
2. **M2 最小闭环**:`cloud_upload` + `cloud_list_versions` + `cloud_restore` 三命令 + 版本时间线 UI。
3. **M3 去重与元数据**:内容哈希去重 + 版本元数据完善。
4. **M4 多设备**:若需多设备同步,补拉取最新版本逻辑。

## 7. 风险

| 风险 | 应对 |
| --- | --- |
| 每次保存都存快照 → 存储膨胀 | 内容哈希去重 + 可配置保留策略(如最多 N 版) |
| 后端未定 → 无法开工 | M1 盘点先行,命令层接口与后端解耦(先定抽象) |
| 大文件上传慢 | 后台异步上传,不阻塞保存;进度提示 |
| 恢复覆盖当前 → 丢改动 | 恢复前自动存当前为临时版本 + 二次确认 |
